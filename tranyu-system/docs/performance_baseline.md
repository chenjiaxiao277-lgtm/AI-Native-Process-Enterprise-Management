## 2. 扩展触发条件说明

满足以下任一条件时，应进入容量扩展评估：

1. 租户数 `> 50`
2. 单租户工作项数量 `> 5 万`
3. 核心接口 `P99 > 2 秒`
4. 数据库 CPU `> 70%`

说明：

- 以上条件不是立即重构的触发器，而是“进入专项评估与压测”的触发器。
- 优先通过索引、SQL 优化、缓存、冷热分离等低成本方式缓解。
- 仅当单体架构在业务层优化后仍无法满足时，再进入更大级别改造。

## 3. 未来扩展方案概述

### 3.1 数据库分片

当前阶段：

- 业务表统一保留 `tenant_id`、`space_id` 作为隔离与检索维度。
- 新增 `db_shard_hint` 字段，为未来分片预留路由标识。

后续可选扩展方向：

- 按租户维度进行逻辑分库
- 大租户独立库，小租户共享库
- 热点表按租户或时间做归档/拆分

### 3.2 缓存分片

当前阶段：

- Redis 继续作为统一缓存实例使用。
- 新增 `cache_shard_hint` 预留字段，为未来缓存路由预留扩展位。

后续可选扩展方向：

- 按租户做缓存分组
- 大租户独立缓存命名空间
- 权限缓存、页面缓存、流程缓存拆分

### 3.3 Flowable 多实例

当前阶段：

- Flowable 继续作为统一执行内核部署。
- 业务层负责租户隔离、空间隔离、权限判断。

后续可选扩展方向：

- 按租户等级拆分 Flowable 实例
- 将超大租户迁移到独立 Flowable 实例
- 通过业务映射表维持 `tenant_id / space_id / processInstanceId` 关系

原则：

- 不改造 Flowable 底层表结构
- 不把租户/权限逻辑下沉到 Flowable
- Flowable 只负责执行，不负责隔离与授权

## 4. 建议的巡检频率

- 每周：记录租户数、核心接口响应时间
- 每月：记录数据库 CPU、慢查询、单租户数据量排行
- 每次大版本发布后：重新更新一轮接口基线
