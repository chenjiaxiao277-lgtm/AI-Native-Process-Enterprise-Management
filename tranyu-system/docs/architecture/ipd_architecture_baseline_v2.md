# IPD 项目架构基线（v2）

> 更新日期：2026-04-01  
> 适用范围：`tranyu-system`（IPD 项目）  
> 说明：本基线替代历史 `LTC` 口径文档，后续需求评审与开发以此为准。

## 1. 架构定位

1. 本项目是 **IPD 多租户企业系统**，不是 LTC 基线项目。
2. 当前阶段采用 **单体分层架构**（先收敛边界，再考虑拆分）。
3. Flowable 6.8.1 仅作为流程执行内核，不承担权限、租户、空间隔离。

## 2. 组织与隔离层级

统一三层模型：

1. `tenant`（租户）

- 企业边界。
- 租户间绝对隔离。

1. `space`（空间）

- 租户下的业务协作边界。
- 同租户多空间默认数据隔离。

1. `resource`（业务资源）

- 工作项类型、工作项实例、字段、附件、流程模板、流程实例、任务、页面布局、角色等。

默认访问范围必须是：`当前 tenant + 当前 space`。

## 3. 分层架构

1. 前端交互层

- 自研 UI（空间配置、工作项管理、流程设计、页面布局、角色管理）。
- 仅负责交互与展示，不做最终安全判定。

1. 业务应用层

- Controller / Service / DTO / VO。
- 对外统一业务 API。

1. 权限与隔离层

- TenantContext / SpaceContext / AuthSubjectContext。
- PermissionEngine（统一授权决策入口）。
- 数据范围裁剪与跨空间授权校验。

1. 流程建模适配层

- 自定义节点/泳道/WBS/页面布局模型。
- 自定义流程模型 -> BPMN XML（动态生成、动态部署）。

1. 执行与存储层

- Flowable 6.8.1 执行流程。
- MySQL 存业务数据。
- Redis 做缓存与权限版本。

## 4. Flowable 边界（强约束）

Flowable 负责：

- 流程定义部署
- 实例推进
- 任务生命周期
- 历史记录

Flowable 不负责：

- 租户隔离
- 空间隔离
- 菜单/字段/节点权限
- 页面布局与表单语义

所有流程动作固定顺序：
`业务鉴权 -> 业务规则校验 -> Flowable API`。

## 5. 权限模型（RBAC + ABAC）

## 5.1 核心主体（权限策略可绑定的主体类型）

后续权限模型中的**主体汇总**固定为下列四类（英文标识用于策略与实现对齐）：

1. **`user`**：自然人用户
2. **`group`**：用户组
3. **`space_role`**：空间角色（成员在空间内的岗位/角色，决定**基础准入**）
4. **`work_item_instance_role`**：**工作项实例角色**（见 5.1.1，决定**实例级**数据与动作权限）

不再单独设计 `process_role` 表，也不再把「流程节点角色」与「工作项实例角色」拆成两套并行概念。

### 5.1.1 工作项实例角色（`work_item_instance_role`）

**统一术语**：本系统中历史上可能出现的「流程节点角色」表述，与「工作项实例角色」视为**同一抽象层**，统一称为 **work_item_instance_role（工作项实例角色）**。

**含义**：

- 该层角色同时约束：
  - **工作项实例的数据权限**（可见范围、可改字段、列表/详情范围等）；
  - **当前流程节点上的动作权限**（审批、驳回、转办、加签等与节点相关的业务动作，仍经业务鉴权后再调 Flowable）。

**与空间角色的分工**：

- **`space_role`**：只决定能否进入空间、能否看到某类配置或入口等**基础准入**，不替代实例上的细粒度授权。
- **`work_item_instance_role`**：在已通过空间准入的前提下，决定**该工作项实例**上真正的数据范围与节点动作是否允许。

**数据模型约束**：

- 不额外引入独立的「流程角色」域表与节点角色并行模型；实例级参与人、候选人、节点职责等均应能归并到 **`work_item_instance_role`** 语义下表达（实现上可与既有实例成员/任务分配表映射，但概念层不再分裂）。

## 5.2 权限域

1. 菜单权限
2. 功能权限
3. 数据权限
4. 字段/附件权限
5. 流程节点权限

## 5.3 决策规则

1. 禁止优先（deny > allow）
2. 无禁止时允许并集生效
3. 未命中策略默认拒绝

## 5.4 决策顺序

1. 租户合法性
2. 空间合法性
3. 主体汇总（`user` + `group` + `space_role` + `work_item_instance_role`）
4. 策略匹配
5. deny 判定
6. allow 判定
7. 默认 deny

## 6. 数据归属与表设计约束

所有业务主表必须显式归属：

- `tenant_id`（必填）
- `space_id`（空间级资源必填）

至少覆盖：

- 工作项类型/字段/布局/角色/流程配置
- 工作项实例与实例数据
- 流程模板/流程实例/流程任务/流程评论
- 空间导航配置、空间关联授权

Flowable `act_`* 表不改结构；业务映射表负责关联：

- `process_instance_id -> tenant_id + space_id + work_item_id`
- `task_id -> tenant_id + space_id + work_item_id`

## 7. 空间隔离与空间关联

1. 同租户多空间默认不互通。
2. 跨空间读取必须命中 `space_relation_auth` 显式授权。
3. 跨空间写入默认禁止（除非新增显式策略并审计）。
4. 空间切换必须触发：菜单、列表、详情、权限缓存全量刷新。

## 8. 页面布局与权限联动规则

最终可展示字段集合：
`页面布局配置 ∩ 数据权限 ∩ 字段权限 ∩ 流程节点状态规则`

说明：

1. 页面配置了字段，不代表用户一定可见。
2. 用户有字段权限，不代表页面一定展示。
3. 节点状态可把字段动态切为隐藏/只读/必填。

## 9. 关键风险与前置治理

1. 空间切换脏缓存 -> 强制刷新策略 + 空间维度缓存 Key。
2. 跨空间串读 -> 服务层统一 `tenant+space` 过滤 + 授权白名单。
3. 权限冲突难排查 -> 提供权限解释接口（命中策略、拒绝原因）。
4. 在途流程受模板变更影响 -> 模板版本化，在途实例绑定版本。
5. 流程图布局与流程语义耦合 -> 前端模型与 BPMN 适配层分离。

## 10. 实施优先级（执行版）

Phase A（P0）：隔离地基

1. 统一上下文（tenant/space/user）
2. 空间级查询强制 `tenant+space`
3. 空间切换全量刷新

Phase B（P0）：权限底座

1. RBAC 主链路
2. 菜单/页面/按钮基础鉴权
3. 权限引擎统一入口

Phase C（P1）：页面布局联动

1. 详情页/新建页规则化
2. 字段权限+节点规则联动

Phase D（P1）：工作项实例角色打通

1. `work_item_instance_role` 在实例与当前节点上的分配/回收（与任务候选人等业务映射一致）
2. 审批等节点动作前置鉴权（业务层，非 Flowable 内建权限）

Phase E（P2）：治理增强

1. ABAC 条件扩展
2. 审计与权限解释
3. 模板版本发布治理

Phase F（P1）：租户扩展性准备（渐进式）

1. 新增租户配置域（`ltc_tenant_config`）：容量配额、租户分层、分片提示位。
2. 新增租户请求指标切面（不侵入业务、不影响返回）：记录 tenant/space/path/duration。
3. 建立性能基线文档并周期更新：租户数、单租户数据量、核心接口 P95/P99、DB 负载。
4. 设定扩展触发阈值：
  - 租户数 > 50  
  - 单租户工作项 > 5 万  
  - 核心接口 P99 > 2s  
  - 数据库 CPU > 70%
5. 触发后的扩展方向（仅方案，不提前拆分）：数据库分片预案、Flowable 多实例预案。

## 11. 架构守卫（必须遵守）

1. 禁止 Controller 直接调用 Flowable 原生 Service。
2. 禁止业务 SQL 缺失 `tenant_id`（空间级缺 `space_id`）。
3. 禁止用默认空间兜底写入数据。
4. 禁止把菜单权限当数据权限替代。
5. 禁止未鉴权直接执行流程动作。

## 12. 验收门禁

1. 切空间后数据、菜单、权限结果全部刷新。
2. 同租户不同空间默认互不可见。
3. 空间授权后仅授权范围可读。
4. 同时命中 allow 与 deny 时最终 deny。
5. `work_item_instance_role` 仅在对应工作项实例及当前节点语义下有效，随实例状态与任务生命周期回收或变更。
6. Flowable 故障时业务层不允许绕过鉴权直接写引擎。
7. 租户监控日志可按 `tenant + space + path` 聚合分析。
8. 达到扩展阈值时，能基于基线文档快速判断扩容路径。
